02 Складність

DNS: як доменне ім'я стає IP-адресою

A AAAA CNAME MX TTL

Що це таке?

DNS (Domain Name System) — це розподілена база даних, яка відповідає за перетворення людиночитаних доменних імен (наприклад, google.com) на машинні IP-адреси (142.250.185.46). Без DNS ти мусив би запам'ятовувати числові адреси кожного сайту.

DNS — це не один сервер, а ієрархічна система з мільйонів серверів, розподілених по всьому світу. Саме вона робить можливим те, що example.com завжди веде на правильний сервер — незалежно де ти знаходишся.

📖 Аналогія з телефонною книгою

DNS — це як телефонна книга інтернету. Ти знаєш ім'я людини (домен), а книга дає тобі номер телефону (IP-адресу). Але на відміну від паперової книги, DNS-книга — глобальна, автоматично оновлюється і кешується на кожному рівні.

Ієрархія DNS-серверів

DNS має чотирирівневу структуру. Коли твій резолвер не знає відповіді, він іде знизу вгору:

// Ієрархія DNS (від найвищого до найнижчого)

1. Root DNS сервери (13 кластерів, по всьому світу)
   └─ Знають адреси всіх TLD-серверів
   └─ Позначаються крапкою: "."

2. TLD (Top-Level Domain) сервери
   └─ .com, .ua, .org, .net, .io тощо
   └─ Знають адреси authoritative серверів для кожного домену

3. Authoritative DNS сервери
   └─ Зберігають реальні записи для конкретного домену
   └─ Відповідають: "example.com → 93.184.216.34"

4. Recursive Resolver (резолвер)
   └─ Твій провайдер або 8.8.8.8 (Google), 1.1.1.1 (Cloudflare)
   └─ Робить всю роботу за клієнта

Повний ланцюжок DNS-запиту

Що відбувається, коли ти вперше запитуєш example.com:

// Крок 1: Браузер перевіряє власний кеш
Браузер: "Чи знаю я вже IP для example.com?"
→ Ні → переходить до ОС

// Крок 2: ОС перевіряє /etc/hosts та системний DNS-кеш
ОС: "Є щось у локальному файлі /etc/hosts?"
→ Ні → звертається до резолвера

// Крок 3: Рекурсивний резолвер перевіряє свій кеш
Resolver: "Чи є відповідь у моєму кеші?"
→ Ні → запит до Root DNS

// Крок 4: Root DNS → TLD
Root: "example.com? Не знаю, але .com → 192.5.6.30"
→ Резолвер: запит до TLD (.com)

// Крок 5: TLD → Authoritative
.com TLD: "example.com? Authoritative → ns1.example.com"
→ Резолвер: запит до Authoritative

// Крок 6: Authoritative → відповідь
Authoritative: "example.com A → 93.184.216.34 (TTL: 3600)"
← Резолвер кешує і повертає клієнту
← Браузер кешує відповідь

DNS-записи — типи

Authoritative сервер зберігає різні типи записів:

ТипПризначенняПриклад
AДомен → IPv4-адресаexample.com → 93.184.216.34
AAAAДомен → IPv6-адресаexample.com → 2606:2800:220:1:248:1893:25c8:1946
CNAMEПсевдонім (аліас) до іншого доменуwww.example.com → example.com
MXПоштовий сервер для доменуexample.com → mail.example.com
TXTДовільний текст (SPF, DKIM, верифікація)"v=spf1 include:..."
NSNameserver — хто відповідає за зонуexample.com → ns1.example.com
TTLЧас кешування відповіді (секунди)3600 = 1 година

TTL та кешування

TTL (Time To Live) — час у секундах, протягом якого відповідь може бути закешована. Після закінчення TTL резолвер повторює запит.

// Типові значення TTL
TTL = 300     // 5 хвилин  — часто змінювані записи
TTL = 3600    // 1 година  — стандарт
TTL = 86400   // 24 години — стабільні сайти

// Чому це важливо?
// При зміні IP (переїзд на новий сервер) DNS-зміни
// поширюються НЕ миттєво — чекати доведеться до закінчення TTL
// Тому перед переїздом зменшують TTL до 300s заздалегідь

Як перевірити DNS у терміналі

# Отримати A-запис (IPv4)
dig example.com A
nslookup example.com         # Windows

# Отримати всі записи
dig example.com ANY

# Трасування повного ланцюжка
dig example.com +trace

# Перевірити конкретний DNS-сервер
dig @8.8.8.8 example.com A    # запитати Google DNS
dig @1.1.1.1 example.com A    # запитати Cloudflare DNS

Як це працює

  1. Браузер перевіряє власний DNS-кеш → кеш ОС → файл /etc/hosts.
  2. Якщо нічого немає — запит іде до рекурсивного резолвера (провайдер / 8.8.8.8 / 1.1.1.1).
  3. Резолвер ітеративно обходить ієрархію: Root → TLD → Authoritative.
  4. Кожен рівень кешує відповідь на час TTL — повний ланцюжок потрібен лише при першому запиті або після закінчення TTL.
  5. IP-адреса повертається браузеру і кешується — наступний запит до того ж домену буде миттєвим.
⚠️ Типові помилки та хибні уявлення
  • «Зміна DNS-запису — миттєва» — ні. Поширення займає від хвилин до 24+ годин залежно від TTL. Перед переїздом зменши TTL до 300s заздалегідь.
  • «www і example.com — це одне й те саме» — ні. www.example.com і example.com — окремі субдомени. www зазвичай задається через CNAME.
  • «CNAME можна поставити на root-домен» — не можна. У @ (root) підтримуються лише A, AAAA, MX, TXT, NS. Деякі провайдери обходять це через ALIAS/ANAME записи.
  • «DNS безпечний» — базовий DNS надсилає запити у відкритому вигляді (UDP 53). Для шифрування використовують DNS-over-HTTPS (DoH) або DNS-over-TLS (DoT).
  • «Один домен — одна IP» — ні. A-записів може бути декілька (round-robin для балансування навантаження або геолокаційний DNS).
⚡ Практика

Відкрий термінал і виконай ці команди (або скористайся dnschecker.org для веб-інтерфейсу):

  1. Виконай dig google.com A — знайди розділ ANSWER, запиши IP-адреси та TTL.
  2. Виконай dig google.com +trace і відстеж повний ланцюжок: Root → .com → google.com authoritative.
  3. Порівняй відповіді від двох різних DNS-серверів: dig @8.8.8.8 google.com і dig @1.1.1.1 google.com. Чи відрізняються IP?
  4. Перевір запис dig google.com MX — знайди поштові сервери Google.
  5. Відкрий DevTools → вкладка Network → завантаж будь-яку сторінку → знайди у Timing запитів колонку "DNS Lookup". Скільки часу зайняв DNS для першого і для повторного запиту?

📋 Розбір типових помилок на співбесідах

Питання: «Поясни, що таке DNS»

❌ «DNS перетворює домени в IP» — правильно, але занадто коротко. Немає розуміння ієрархії і процесу.

✅ Поясни ієрархію (Root → TLD → Authoritative), роль резолвера, кешування з TTL і наведи конкретний приклад запиту для google.com.

Питання: «Що таке CNAME і коли його використовують?»

❌ «CNAME — це псевдонім» — без контексту коли і де застосовується.

✅ CNAME — псевдонім домену до іншого домену. Використовують для www → example.com, CDN-аліасів. Не можна на root-домені — там тільки A/AAAA.

Питання: «Чому DNS-зміни не вступають в силу одразу?»

❌ «Треба чекати» — не пояснює механізм.

✅ Через TTL: кожен резолвер кешує відповідь на цей час. При TTL=86400 (24год) старе значення може зберігатися до 24 годин у різних резолверів по світу. Рішення — зменшити TTL до мінімуму (300s) за 24-48 годин до зміни.

✨ Цікаві фішки
  • Cloudflare 1.1.1.1 і Google 8.8.8.8 — публічні DNS-резолвери. Їх часто прописують вручну для швидшого або безпечнішого DNS (DNS-over-HTTPS).
  • DNS cache poisoning — атака, при якій зловмисник підробляє DNS-відповіді. Захист — DNSSEC (цифровий підпис DNS-записів).
  • В Chrome можна перевірити DNS-кеш прямо у браузері: chrome://net-internals/#dns — там видно закешовані домени та їх адреси.
  • Деякі домени мають сотні A-записів (як Google) — це round-robin DNS: кожен запит отримує різні IP для балансування навантаження між серверами.
  • Файл /etc/hosts на Mac/Linux (або C:\Windows\System32\drivers\etc\hosts на Windows) обходить DNS повністю — локальні записи там завжди мають пріоритет. Саме так розробники тестують сайти локально через реальний домен.
