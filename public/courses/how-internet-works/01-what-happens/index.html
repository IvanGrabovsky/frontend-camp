01 Складність

Що відбувається коли вводиш URL у браузер?

DNS TCP/IP HTTP TLS Rendering

Що це таке?

Кожного разу, коли ти вводиш адресу в браузер і натискаєш Enter, запускається складний ланцюжок подій — від перетворення доменного імені на IP-адресу до малювання пікселів на екрані. Розуміння цього шляху — фундамент для будь-якого веб-розробника.

Це питання — одне з найпопулярніших на технічних співбесідах. І не просто так: відповідь показує, наскільки глибоко ти розумієш веб.

📬 Аналогія з життя

Уяви, що ти надсилаєш лист другу. Ти пишеш на конверті адресу (URL). Пошта (DNS) знаходить будинок за адресою. Листоноша (TCP) доставляє конверт, чекає підтвердження отримання. А якщо лист секретний — його запечатують у спецконверт (TLS). Друг отримує лист, розпаковує (парсинг HTML), і читає зміст (рендеринг).

Повний шлях запиту — крок за кроком

Крок 1: Парсинг URL

Браузер розбирає введений рядок на складові частини:

// Структура URL
https://www.example.com:443/about?lang=ua#team
  │         │            │    │      │       │
  │         │            │    │      │       └─ fragment (якір)
  │         │            │    │      └─ query string (параметри)
  │         │            │    └─ path (шлях)
  │         │            └─ port (порт, 443 для HTTPS)
  │         └─ host (домен)
  └─ scheme (протокол)

Якщо ти ввів просто example.com, браузер автоматично додасть https://. Якщо ввів щось без крапки — спробує це як пошуковий запит (Google, Bing тощо).

Крок 2: Перевірка кешу

Перед тим як кудись йти, браузер перевіряє чи немає відповіді вже готової:

  1. Кеш браузера — чи є збережена сторінка і чи вона ще «свіжа» (Cache-Control, Expires).
  2. Кеш DNS — чи браузер вже знає IP-адресу цього домену.
  3. Кеш ОС — чи є запис у файлі /etc/hosts або системному DNS-кеші.

Якщо знайшли актуальний кеш — сторінка з'являється миттєво. Якщо ні — починається мережевий запит.

Крок 3: DNS-резолюція

Браузер повинен з'ясувати IP-адресу сервера. Для цього він звертається до DNS-резолвера (зазвичай від інтернет-провайдера).

// Ланцюжок DNS-запитів
Браузер → DNS-резолвер провайдера
  → Root DNS сервер        (каже: ".com — питай у TLD сервера")
  → TLD сервер (.com)      (каже: "example.com — питай у authoritative")
  → Authoritative DNS      (каже: "IP = 93.184.216.34")
← Результат: 93.184.216.34

Кожен крок може бути закешований. Тому повний ланцюжок відбувається не кожного разу — зазвичай резолвер вже знає відповідь.

Крок 4: TCP-з'єднання (3-way handshake)

Тепер браузер знає куди йти. Він встановлює надійне з'єднання з сервером через протокол TCP:

// Трьохстороннє рукостискання
Клієнт  → SYN         → Сервер     ("Привіт, хочу зʼєднатися")
Клієнт  ← SYN-ACK    ← Сервер     ("Ок, я готовий")
Клієнт  → ACK         → Сервер     ("Чудово, починаємо!")
// З'єднання встановлено — можна передавати дані

Навіщо три кроки? Щоб обидві сторони переконалися, що канал зв'язку працює в обох напрямках. Це як телефонний дзвінок: «Алло?» — «Так, чую!» — «Ок, говоримо».

Крок 5: TLS Handshake (для HTTPS)

Якщо сайт використовує HTTPS (а це 95%+ сучасного вебу), після TCP-з'єднання починається ще один «рукостиск» — вже для шифрування:

  1. Client Hello — браузер каже: «Я підтримую ось такі алгоритми шифрування».
  2. Server Hello — сервер обирає алгоритм і відправляє свій SSL-сертифікат.
  3. Перевірка сертифіката — браузер переконується, що сертифікат виданий надійним Certificate Authority (CA) і не протермінований.
  4. Обмін ключами — генерується спільний секретний ключ (зазвичай через алгоритм Diffie-Hellman).
  5. Все подальше спілкування зашифроване симетричним шифруванням (швидше ніж асиметричне).

Крок 6: HTTP-запит

Нарешті! Браузер надсилає справжній запит:

// HTTP-запит (GET)
GET /about HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) Chrome/120
Accept: text/html,application/xhtml+xml
Accept-Language: uk-UA,uk;q=0.9,en;q=0.8
Accept-Encoding: gzip, br
Connection: keep-alive
Cookie: session_id=abc123; theme=dark

Крок 7: Відповідь сервера

Сервер обробляє запит і надсилає відповідь:

// HTTP-відповідь
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 5842
Content-Encoding: gzip
Cache-Control: max-age=3600
Set-Cookie: visited=true; Path=/; HttpOnly

<!DOCTYPE html>
<html>...

Статус-код 200 означає «все ок». Інші важливі: 301 (переїхали), 404 (не знайдено), 500 (помилка сервера).

Крок 8: Rendering Pipeline

Тепер починається найцікавіше — браузер перетворює HTML-текст на пікселі:

// Rendering pipeline браузера
HTML-байти → Символи → Токени → DOM-дерево
CSS-байти  → Символи → Токени → CSSOM
                                   ↓
              DOM + CSSOM → Render Tree
                                   ↓
                              Layout (розміри, позиції)
                                   ↓
                              Paint (кольори, тіні, текст)
                                   ↓
                              Composite (шари → GPU → екран)
  1. DOM — дерево HTML-елементів. Кожен тег стає вузлом.
  2. CSSOM — дерево CSS-правил, обчислених для кожного елемента.
  3. Render Tree — тільки видимі елементи (без display: none, <head> тощо).
  4. Layout — браузер обчислює точні розміри та координати кожного блоку.
  5. Paint — малює кольори, текст, тіні, рамки у растрове зображення.
  6. Composite — складає окремі шари та відправляє на GPU для відображення.

Крок 9: Додаткові ресурси

Поки браузер парсить HTML, він знаходить посилання на інші ресурси і завантажує їх паралельно:

  • <link rel="stylesheet"> — CSS-файли (блокують рендеринг)
  • <script> — JavaScript (блокує парсинг HTML, якщо без async/defer)
  • <img> — зображення (завантажуються асинхронно)
  • @font-face — шрифти (можуть викликати FOIT/FOUT)

Кожен ресурс проходить подібний цикл: DNS → TCP → (TLS) → HTTP → відповідь. Але завдяки HTTP/2 і keep-alive з'єднання, повторні DNS та TCP-кроки зазвичай не потрібні.

Ключові метрики швидкості

МетрикаЩо вимірюєОрієнтир
RTTRound Trip Time — час на повну подорож запиту і відповіді< 100ms
TTFBTime to First Byte — час до першого байту відповіді від сервера< 200ms

⚠️ Типові помилки та хибні уявлення
  • «URL і домен — це одне й те саме» — ні. Домен (example.com) — лише частина URL. URL включає протокол, шлях, параметри тощо.
  • «HTTPS — це інший протокол» — ні. Це звичайний HTTP, обгорнутий у TLS-шифрування. Сам HTTP-запит ідентичний.
  • «Браузер робить один запит на сторінку» — ні. Типова сторінка генерує 50–200 HTTP-запитів (CSS, JS, зображення, шрифти, трекери).
  • «DNS-запит відбувається кожного разу» — ні. DNS-відповіді кешуються (TTL зазвичай 300–86400 секунд). Повний ланцюжок root→TLD→authoritative — рідкість.
  • «CSS не впливає на швидкість» — впливає! CSS є render-blocking ресурсом. Поки браузер не завантажить і не розпарсить весь CSS, він не почне рендерити сторінку.
⚡ Практика

Відкрий DevTools у браузері (F12 або Cmd+Option+I) і виконай ці завдання:

  1. Відкрий вкладку Network, перезавантаж будь-яку сторінку, і знайди перший HTML-запит. Подивися на заголовки запиту (Request Headers) та відповіді (Response Headers). Запиши що побачив.
  2. У тій же вкладці Network знайди загальну кількість запитів і загальний розмір завантажених даних (внизу панелі). Скільки запитів робить Google.com? А YouTube?
  3. Відкрий вкладку Performance, натисни Record і перезавантаж сторінку. Знайди на таймлайні: FCP, LCP, Layout, Paint. Зроби скріншот.
  4. У консолі DevTools введи performance.timing (або performance.getEntriesByType('navigation')[0]) і порахуй TTFB: responseStart - requestStart.

📋 Розбір типових помилок на співбесідах

Питання: «Що відбувається коли вводиш URL?»

❌ «Ну, браузер відправляє запит на сервер і отримує HTML» — це правильно, але надто поверхнево. Інтерв'юер чекає деталей.

✅ Розкажи по кроках: парсинг URL → кеш → DNS → TCP → TLS → HTTP-запит → відповідь → парсинг → рендеринг. Не забудь про паралельне завантаження ресурсів.

Питання: «Як працює HTTPS?»

❌ «HTTPS — це захищений протокол» — не пояснює механізм.

✅ Поясни TLS handshake: Client Hello → Server Hello + сертифікат → верифікація → обмін ключами → симетричне шифрування. Асиметричне — тільки для початкового обміну.

Питання: «Що таке Critical Rendering Path?»

❌ Плутають DOM і Render Tree або забувають про CSSOM.

✅ HTML → DOM, CSS → CSSOM, DOM + CSSOM → Render Tree → Layout → Paint → Composite. Render Tree не включає display: none і <head>.

✨ Цікаві фішки
  • У Chrome DevTools є вкладка Security — там можна побачити деталі TLS-з'єднання: версію протоколу, алгоритм шифрування, хто видав сертифікат.
  • Команда dig example.com (або nslookup на Windows) покаже весь DNS-ланцюжок прямо в терміналі.
  • Один TCP-пакет може нести максимум ~1460 байтів корисних даних (MTU). Якщо HTML більший — він розбивається на кілька пакетів.
  • HTTP/2 дозволяє мультиплексування — кілька запитів одночасно через одне TCP-з'єднання (замість 6 паралельних з'єднань у HTTP/1.1).
  • Preconnect (<link rel="preconnect">) дозволяє зробити DNS + TCP + TLS заздалегідь, ще до того як браузер знайде ресурс в HTML.
  • Lighthouse у DevTools автоматично вимірює всі ключові метрики (FCP, LCP, CLS) і дає конкретні рекомендації щодо покращення.
